# design-tokens-v1 · 驾驶舱设计 tokens 跨模块契约

- 版本：v1.1（2026-09-07，见文末修正案 A：分区色按角度算色相）· 原 v1.0（2026-08-08）· 属主：CFO · 依据：PRD cockpit-v1 §2/§3（用户已批准）
- 消费方：nginx-docker（产出并注入 `/__cockpit/tokens.css`）、ring / table / gantt / auth
  （各留兜底块）、对比度校验脚本（A1）、兜底漂移校验（A3）
- **本表是全站颜色与主题行为的唯一事实源。** 改色先改这里，再改 tokens.css，
  最后机械同步各仓兜底块（铁律 4 / 11）。

## 1. 三条轴

| 轴 | 取值 | 载体 | 持久化 |
|---|---|---|---|
| 明暗 | `light` / `dark`（默认跟随系统） | `html[data-theme]` | `localStorage["cockpit-theme"]`（`light|dark|auto`） |
| 预设主题色 | `teal`（默认）/ `violet` / `amber` | `html[data-accent]` | `localStorage["cockpit-accent"]` |
| （模块自留） | 甘特「显示已完成」 | —— | `localStorage["cockpit-gantt-showdone"]`（归 gantt，登记于此防撞名） |

多窗同步：三者变更均靠 `storage` 事件即时生效，无刷新。

## 2. 语义规则（规范性）

- **计划紫 / 事实青是信息，不是装饰**：`--plan*` / `--fact*` 表达两本台账，
  **不随预设主题色变**。换预设换的是 `--accent*` 族——按钮、页签下划线、品牌记号、
  焦点这类「机身颜色」。把台账色做成可换，等于允许把数据重新贴标签。
- 默认预设 `teal` 的 accent 取值 == 事实青族（保留「按下去就是在产生事实」的语义）；
  `violet` / `amber` 预设下 accent 与图表中的计划紫 / 警示琥珀同族——
  **机身 ≠ 数据标记**，上下文不同，允许同族（本裁决记档，夜班 CFO 自决）。
- 模块 CSS/JS **禁裸 hex**，只准 `var(--…)`；唯一豁免：兜底块本身（A2）。

## 4. 校验（规范性 · A1/A2/A3 的口径）

- **A1 对比度矩阵**：脚本解析本表「对比度/门限」列出现的全部组合 ×（3 预设 × 明暗），
  实算 WCAG 比值，任一低于门限即红。脚本落 `nginx-docker review/reviewcode/`。
- **A2 禁裸 hex**：模块 CSS/JS 颜色字面量零容忍，兜底块（带哨兵注释
  `/* tokens-fallback:begin */ … /* tokens-fallback:end */`）豁免。落各仓 reviewcode。
- **A3 兜底漂移**：兜底块必须与本表生成的标准块**逐字节一致**（含全部 3 预设）；
  diff 脚本落各仓 `scripts/checks/`，commit 时拦。

## 5. 注入与兜底（行为契约，nginx-docker v0.6 收录细节）

- nginx 向 ring/table/gantt 三页注入：`</head>` 前 boot 脚本（读两个 localStorage 键、
  设 `data-theme`/`data-accent`，**不发请求、不摸 documentElement 以外的 DOM、≤10 行**），
  `</body>` 前 `tokens.css` + navbar 资产。锚点判据：每页 `</head>`、`</body>` 各恰好一个。
- login 不注入：自带兜底块（**含全部 3 预设**）+ 自带同款 boot 逻辑。
- 覆盖顺序：注入的 tokens.css 后加载，层叠必胜兜底块；兜底允许滞后于本表一个版本，
  但 A3 会把「滞后」变成显式红——同步是机械活，派 codex。

## 6. 变更流程

1. 改本表（CFO，版本号 bump + 修正记录）
2. nginx-docker 同步 `/__cockpit/tokens.css`（A1 重跑）
3. 四仓兜底块机械同步（A3 变绿）
- 新增预设 = 3.3 加一节 + 全链路重跑，禁止跳过 A1 直接加色。

# 修正案 A · 分区色：按角度算色相（v1.1 · 2026-09-07）

- 属主：CFO · 依据：人类裁决 2026-09-07（「分区按角度变可以」「契约有必要改一改」）
- 消费方：`code/table`（蜂巢行动分区，第一个实现者）

## A.0 为什么要修正案（原契约的盲区）

v1.0 假设**颜色是一张可枚举的表**：每个 token 一个固定值，A1 逐个实测。
这套在「按钮是什么绿」上完全够用。

但蜂巢行动分区提出了 v1.0 没考虑过的形状：**分区数量不固定**（现在 9 个，以后可能 15 个），
而人类要求「**按角度定颜色**」——分区在蜂巢上占哪个角度，就用那个角度的色相。
颜色因此是**位置的连续函数**，不是一张有限的表。

固定坑位（比如预定义 12 个分区色）被否掉了，人类的理由：**分区数可能大于 12**。
CFO 补充一条更根本的：固定坑位下**颜色与空间位置无关**——分区在 3 点钟方向、颜色却是
「第 7 号色」，两套编号互不相干，记不住。按角度定色则把两者合一：
记的不是「某个分区是绿的」，是「那个分区在左上，左上是绿的」。

**代价（人类已确认接受）**：新增分区会重分扇区角度，**所有分区颜色都会挪一点**。
这是颜色与位置绑定的必然结果，也正是它的价值——两者永远一致。

## A.1 拆开「谁定什么」（本修正案的要害）

v1.0 的红线「模块禁裸 hex」**不变**。调和办法是把颜色的三个分量分开授权：

| 谁定 | 定什么 | 为什么可以这么分 |
|---|---|---|
| **本契约 / tokens.css** | 明度 `L`、彩度 `C`（深浅各一组） | **对比度几乎只由 L/C 决定** |
| **模块** | 只算色相 `H` = 该分区的扇区角度 | 转色相不改对比度 |

依据是 OKLCH 的感知均匀性：同一个 `L` 在红、在绿、在蓝**看起来一样亮**，
所以固定 `L`/`C` 就固定了对比度，`H` 可以自由转。
（HSL 没有这个性质——`hsl(60,50%,50%)` 的黄比 `hsl(240,50%,50%)` 的蓝亮得多。
**所以本修正案只准用 `oklch()`，不准用 `hsl()`。**）

模块里允许出现的唯一形态：

```css
oklch(var(--zone-l) var(--zone-c) <角度>deg)
```

**明度彩度必须来自 var()，一个数字都不许写死。** 模块只提供角度。
这不构成「裸 hex」——A2 扫的是硬编码色值，这里没有。

## A.2 token（规范性 · 数值即法律）

| token | light | dark | 说明 |
|---|---|---|---|
| `--zone-l` | `0.62` | `0.70` | OKLCH 明度 |
| `--zone-c` | `0.09` | `0.09` | OKLCH 彩度（低饱和，人类明确要求） |

**明色是瓶颈**：白底上 `L > 0.66` 时最差色相跌破 3。`0.62` 留了余量。

## A.3 实测对比度（全色相扫描，非估算）

底：light `#FFFFFF` / dark `#151C2E`。扫全部 360 个整数色相、排除 A.4 禁用带后取最差值。

| 主题 | 最差 | 最好 | 门限 | |
|---|---|---|---|---|
| light | **3.48**（H=163°） | 3.82 | ≥3（图形档） | ✅ |
| dark | **6.08**（H=353°） | 6.62 | ≥3 | ✅ |

12 个代表色相实测（供 A1 复核用）：

| H | light 对比度 | dark 对比度 |
|---|---|---|
| 0° | 3.82 | 6.08 |
| 30° | 3.79 | 6.12 |
| 60° | 3.73 | 6.22 |
| 90° | 3.65 | 6.35 |
| 120° | 3.56 | 6.49 |
| 150° | 3.50 | 6.60 |
| 180° | 禁用带 | 禁用带 |
| 210° | 3.52 | 6.57 |
| 240° | 3.59 | 6.44 |
| 270° / 300° | 禁用带 | 禁用带 |
| 330° | 3.81 | 6.10 |

> 同 v1.0 的教训：这些是**跑出来的**，不是估的。改 `--zone-l`/`--zone-c` 必须重跑全色相扫描。

## A.4 禁用色相带（规范性）

v1.0 §2 定死「**计划紫 / 事实青是信息，不是装饰**」。分区色是装饰性分类，
落进台账色的色相带会让人误以为分区在表达「计划/事实」——**语义污染，比难看严重**。

实测台账色的 OKLCH 色相：

| token | 色相 |
|---|---|
| `--plan` light `#6D5AE6` / dark `#9B8CFF` | 284.0° / 287.4° |
| `--fact` light `#0B7A6F` / dark `#2FD4C2` | 183.8° / 183.6° |

**禁用带**（各取 ±20°）：

- `164° – 204°`（事实青）
- `264° – 304°`（计划紫）

分区角度落进禁用带时，**顺时针偏出该带的最近边界**。
可用色相共 `360 - 80 = 280°`。

## A.5 显式设色仍然优先

分区在 planner 里显式设过颜色（非默认灰 `#999999`）时**用它自己的**，不参与按角度算色。
这条沿用 v1.0 的既有行为，本修正案不改。

⚠️ 已实测：9 个分区里 **7 个是默认灰**，只有一个分区设过 `#4a90d9`。
所以实现**不能直接读 `zone.color` 就完事**，必须判它是不是默认值。

## A.6 校验

- **A1**：新增一条——按 A.2 的 L/C 扫全部 360 色相（排除 A.4 禁用带），最差值须 ≥3
- **A2**：模块里出现 `oklch(` 且明度彩度不是 `var(--zone-l)`/`var(--zone-c)` 的，判红
- **A2 补充**：模块里出现 `hsl(` 拼色值的，判红（本修正案只准 `oklch()`）
- **A3**：`--zone-l` / `--zone-c` 纳入兜底块同步

## A.7 变更流程（沿用 §6）

改 A.2 的数值 → 重跑全色相扫描填 A.3 → nginx-docker 同步 tokens.css → 四仓兜底块同步。
**禁止跳过全色相扫描直接改 L/C。**
