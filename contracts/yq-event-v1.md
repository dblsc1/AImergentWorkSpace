# yq-event/v1 —— 开放事件标准

> **状态**：v1 规范性。**本文件是事件格式的对外唯一事实。**
> **权威链**：本文件由 `agents/CONSTITUTION.md` §2.1–§2.5 授权并与之逐条对应。
> 两者若不一致 → **停下上报人类**，不许自行取舍。
> `agents/reference/HANDOFF.md` 是讨论草稿，**不是判据**（它内部已知自相矛盾）。
>
> **兼容承诺**：**信封字段只增不改不删。** 扩展 = 新增 `type`，不改信封。
> 真不兼容只能发 v2，新旧并行。本文件一经发布即有外部消费方（课程学生），
> 改它等于改别人已经写好的作业。

## 1. 这是什么

系统里发生的每件事都写成一个 JSON，投进**唯一的写入口**。

- **信封**：所有事件共用，永不变形。
- **载荷 `data`**：按 `type` 各不相同。

**消费者必须静默忽略自己不认识的 `type`**（Postel 法则）。
这条是整个扩展策略的基石：花园只订阅成长相关 type，圆环只看 `session.*`，互不干扰；
新增视图 = 新增一条读路径，现有代码零改动。

自有后端与外部用户**走同一个入口**——接口文档因此天然被验证。

## 2. 信封

```jsonc
{
  "spec":       "yq-event/v1",
  "id":         "evt_a1b2c3",
  "dedupeKey":  "timer:sess_20260729_01",
  "type":       "session.completed",
  "user":       "u_local",
  "source":     "timer-backend",
  "time":       "2026-07-29T10:00:00+08:00",
  "recordedAt": "2026-07-29T10:00:03+08:00",
  "subject":    { "tier2": "学习", "tier3": "英语",
                  "project": "p_1", "task": "t_45" },
  "data":       { "durationSeconds": 1800 },
  "flags":      ["no_growth"],
  "ai":         { "generated": true, "confidence": 0.87, "confirmed": true }
}
```

| 字段 | 必填 | 类型 | 说明 |
|---|---|---|---|
| `spec` | ✅ | string | 固定 `"yq-event/v1"` |
| `id` | ✅ | string | 本条事件的标识。**不是防重键** |
| `dedupeKey` | ✅ | string | 防重键，见 §3 |
| `type` | ✅ | string | 事件类型，见 §6 |
| `user` | ✅ | string | 认证后置期恒为 `"u_local"` |
| `source` | ✅ | string | 谁报的（`timer-backend` / 学生自定义） |
| `time` | ✅ | string | **事情发生的时间**，ISO8601 带时区，见 §4 |
| `recordedAt` | ✅ | string | **系统收到的时间**，服务端盖章，见 §4 |
| `subject` | ✅ | object | 见 §5 |
| `data` | ❌ | object | 按 `type` 定型，见 §6 |
| `flags` | ❌ | string[] | 默认 `[]`，见 §7 |
| `ai` | ❌ | object | `{generated, confidence, confirmed}` |

## 3. 防重：`dedupeKey`，**不是** `id`

**唯一约束 = `(user, source, dedupeKey)`。** 同一防重键重复提交只生效一次。

`id` 与 `dedupeKey` 是**两个不同的东西，不许当同义词实现**：

| | `id` | `dedupeKey` |
|---|---|---|
| 是什么 | 这一条事件的标识 | **业务意义上"同一件事"的键** |
| 同一件事重试提交 | **可以不同** | **必须相同** |

**按 `id` 判重 = 防重完全失效**——重试时 `id` 变了，系统会当成新事件，
学生重复提交会重复长树。

`dedupeKey` 由**产生方**负责给出且必须稳定。例：计时器用 session 标识、
日记链路用日记标识。（这是花园现有"按日记防重复"从 `diaryId` 泛化而来。）

## 4. 双时间：`time` 与 `recordedAt`

**两个字段各管各的，不许合并成一个。**

| 字段 | 含义 | 谁给 | 用途 |
|---|---|---|---|
| `time` | **事情发生的时间**——展示给用户的那个 | 客户端提供，**可以是过去** | 花园长在哪一天、统计归到哪一天 |
| `recordedAt` | **系统收到的时间** | **服务端盖章，客户端说了不算** | 重放排序、审计、对账 |

**为什么必须两个**：学生要能补交昨天的记录（`time` 在昨天），
而重放与排序必须不受补交扰动（按 `recordedAt`）。
**合成一个字段就必然牺牲其中一件。**

`recordedAt` **永不可改**；`time` 一经提交也不可改。
要改历史 = **追加修正事件**，不改写既有事件。

## 5. `subject`：分类轴对外，内部 ID 对内

```jsonc
"subject": {
  "tier2":   "学习",   // ✅ 必填。受控分类词表
  "tier3":   "英语",   // ✅ 必填。学生只需写这两个
  "project": "p_1",    // ❌ 选填。仅系统内部产生的事件才有
  "task":    "t_45"    // ❌ 选填。外部事件留空即合法
}
```

**`tier2` / `tier3` 不是"分区的名字"和"项目的名字"，而是一套受控的分类词表。**

这个区别是全部要害：

- 若它是**可变实体的显示名** → 改个名就污染全部历史
- 作为**分类标签** → 分类是**它自己的事实，不是别人的副本**，
  分区/项目怎么改名都不触碰它

这也本就符合成长模型：树按 `tier2`+`tier3` 生长，每个小分类 10 个阶段——
**分类轴是一等的领域概念**，不是项目名的复制品。

两条配套硬约束：

1. **可变实体的显示名一律不进事件。** 项目改名 = 追加 `project.renamed` 事件；
   视图读取时按 ID 现查名字。
2. **`project` / `task` 永远选填。** 外部事件没有它们照样合法——
   这是"自有后端与学生走同一入口"能成立的前提，不是宽容。

> **设计依据**（通行经验）：事件字段自第一天起即视为公开 API，改名/删字段都要迁移方案；
> 归一化还是反归一化取决于耦合度——内部紧耦合用 ID（改名安全、可 join），
> 外部松耦合用副本（对方拿不到你的 ID）；CloudEvents 的 `subject` 是给中间件
> 做过滤路由的，不是塞领域对象的地方。
> 本项目**同时有两类消费方且需求相反**（投影要 ID，学生拿不到 ID），故分层。

## 6. 首批事件类型

| `type` | `data` 载荷 | 说明 |
|---|---|---|
| `session.completed` | `durationSeconds`, `startAt` | 一段计时结束（系统心跳） |
| `task.created` | `kind` | 任务创建留痕 |
| `task.done` | — | 任务完成 |
| `growth.granted` | `amount`, `note` | 通用成长点（**学生入门用的最简类型**） |
| `diary.extracted` | 结构化分类、备注 | 日记链路泛化 |
| `plan.updated` | 变更摘要 | 计划修改留痕（审计用） |

**学生入门只需要：信封 + `growth.granted`。**

## 7. `flags`

- 贴在事件上的字符串数组，如 `["no_growth"]`。
- **贴什么贴纸 = 数据入库时决定；每张贴纸导致什么行为 = handler 代码焊死。**
  改行为必须改代码、过 review。
- **暂行：任何 `source` 都可以贴**，包括学生脚本。
  后果：学生可以给自己的事件贴 `no_growth`，系统会认。
- **本条是「暂行」，不是永久承诺。** 将来收紧只需加一份"仅系统可贴"的清单，
  **不改信封**，因此不违反只增不改不删。

已定义的 flag：

| flag | 行为 |
|---|---|
| `no_growth` | 成长类 handler 首行检查后直接返回——不长树 |

## 8. 两种接入门

1. **文件导入**（入门，零网络知识）：网页上传 `.json` → `POST /api/core/events/import`
2. **API 推送**（进阶）：`POST /api/core/events`，带账户 token

## 9. 最简可用样例（学生照抄这个就能跑）

```json
{
  "spec": "yq-event/v1",
  "id": "evt_my_first_001",
  "dedupeKey": "my-script:2026-07-29:reading",
  "type": "growth.granted",
  "user": "u_local",
  "source": "my-study-script",
  "time": "2026-07-29T21:00:00+08:00",
  "recordedAt": "2026-07-29T21:00:02+08:00",
  "subject": { "tier2": "学习", "tier3": "阅读" },
  "data": { "amount": 1, "note": "读完一章" }
}
```

注意：**没有 `project` / `task` 也是合法的**——这正是 §5 第 2 条的意思。
`recordedAt` 由服务端盖章，客户端填了也会被覆盖。

## 10. 边界样例（实现必须按这些断言）

| # | 输入 | 期望 |
|---|---|---|
| B1 | 同一 `(user, source, dedupeKey)` 提交两次，`id` 不同 | **只生效一次** |
| B2 | 同一 `(user, source)` 下 `dedupeKey` 不同、`id` 相同 | **两条都生效**（`id` 不是防重键） |
| B3 | 缺 `dedupeKey` | 拒绝，**不许回退成用 `id`** |
| B4 | 缺 `tier2` 或 `tier3` | 拒绝 |
| B5 | 只有 `tier2`/`tier3`，无 `project`/`task` | **接受**（外部事件的正常形态） |
| B6 | 客户端自带 `recordedAt` | **服务端覆盖**，以服务端为准 |
| B7 | `time` 在过去（补交） | 接受；统计归到 `time` 那天，重放排序仍按 `recordedAt` |
| B8 | 不认识的 `type` | **静默忽略，不报错**（Postel） |
| B9 | 信封多出未知字段 | 接受并原样保留（只增不改不删的另一面） |
| B10 | `flags:["no_growth"]` 来自外部 `source` | **接受并生效**（§7 暂行条款） |
