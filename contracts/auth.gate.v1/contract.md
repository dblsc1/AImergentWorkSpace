# auth.gate.v1 —— 一道登录门（开放契约）

> **契约 id**：`auth.gate.v1`。
>
> **状态**：v1，规范性。本文件描述的每一条行为都能在 `stub/auth_stub.py` 里找到
> 对应代码，行号引用见各节——**不确定的地方以代码为准，不是以这份文档的措辞为准**。
> 若未来 stub 改了行为却没同步改这里，或者这里写的东西 stub 根本做不到，说明二者
> 出现了分歧，**先改契约、再改代码**（模块 + 契约 + 组装层这套结构的基本纪律）。
>
> **版本号语义**：`v1` 之内只接受**不破坏现有消费方**的追加式变更——例如新增一个
> 可选响应字段、新增一条不影响现有四条端点的新端点。任何会改变**现有端点**的状态码
> 含义、请求/响应形状，或者收紧/放松下面「三条不变量」任何一条的改动，都是**破坏性
> 变更**，必须发布 `auth.gate.v2` 并与 `v1` 并行存在，不能直接在 `v1` 名下改字义。
> 理由很直接：契约一经发布，唯一耦合点就是这个 id——任何换掉 `auth.gate.v1` 实现的
> 人，都是照着这份文档的承诺去接的；在原地改承诺，等于在没人知情的情况下抽换
> 别人已经接好的东西。

## 这个契约是什么 / 不是什么

**是**：一道门。校验"敲门的人知不知道那个共享口令"（或任何等价的会话机制），通过
就发一个会话凭证，之后每次访问受保护资源前验一次这个凭证。`auth_stub.py` 的模块级
docstring 把这句话写在最前面："一道门，不是账号系统"（`auth_stub.py:2`），四个端点
全部只服务这一个目的，没有第五个隐藏用途。

**不是**：账号系统。以下能力全部**不在契约内**，任何人换实现时都不许假设它们存在：

| 能力 | 状态 |
|---|---|
| 注册 / 建新用户 | 不在契约内 |
| 多用户（区分"是谁"登录的） | 不在契约内——stub 里根本没有"用户"这个概念，`verify` 只回答"知不知道口令"，不回答"是谁" |
| 找回密码 | 不在契约内——没有密码之外的凭证恢复路径 |
| 权限分级（普通用户/管理员…） | 不在契约内——门只有"过"与"不过"两态 |
| 第三方登录（OAuth/SSO/…） | 不在契约内 |
| 监护人同意 / 年龄校验 | 不在契约内 |

代码证据：`do_GET`/`do_POST` 只认 `/api/auth/health`、`/api/auth/verify`、
`/api/auth/login`、`/api/auth/logout` 四条路径（`auth_stub.py:152-168`），别的路径一律
`404`；文件里没有用户表、没有角色字段、没有第三方回调路由。

**为什么划这条线**：开源版面向"随便什么人 clone 下来自己跑"，不该替所有下游用户
预先做"要不要上一套真实账号系统"这个决定——捆绑账号系统意味着替他们背下注册流程、
密码存储、找回邮件这些安全责任，而多数自用/小团队场景根本用不上。契约把"门"和
"账号系统"拆成两层：需要多用户的人只需要写一个同样实现这四个端点、同样三条不变量、
同样 cookie 属性的新服务替掉 `stub/`，**反代（nginx）那边一行都不用改**——因为 nginx
只认路径和状态码，根本不知道背后是一个标准库脚本还是一整套账号数据库。这正是"模块只
依赖契约 id，不依赖别的模块"这条结构原则在 auth 这个位置上的具体体现。

## 四个端点

全部前缀 `/api/auth/`；不在这四条路径之内的请求，`do_GET`/`do_POST` 一律返回 `404`
（`auth_stub.py:158-159`、`167-168`），无 body。

### `GET /api/auth/health`

| | |
|---|---|
| 请求体 | 无 |
| `200` | `{"status":"ok"}`（`Content-Type: application/json`） |

代码：`auth_stub.py:153-154`。健康检查**不做任何凭证校验**——它必须对没登录的探测器
（容器编排的健康检查探针）也能打通，否则健康检查本身会被自己的门拦住。

### `GET /api/auth/verify`

| | |
|---|---|
| 请求体 | 无；读取 `Cookie` 请求头里名为 `cockpit_session` 的值 |
| `204` | cookie 存在且签名有效、未过期——**无 body** |
| `401` | cookie 缺失 / 签名不对 / 已过期 / 校验过程抛出任何异常——**无 body** |

代码：路由在 `auth_stub.py:155-157`，判定逻辑在 `89-103`（`token_valid`）。**这两个
状态码之外，`verify` 不会返回别的任何状态码**——它是专给 nginx `auth_request` 用的
内部端点，见下面「三条不变量」第 1、3 条。

### `POST /api/auth/login`

| | |
|---|---|
| 请求体 | JSON 对象：`{"password": "<string>"}` |
| `204` | 口令正确——响应带 `Set-Cookie`（新签发的会话 token），**无 body** |
| `401` | 口令不正确（含请求体为空、或 JSON 里没有 `password` 字段时按空串比对，同样判定为不正确）——**无 body** |
| `400` | `Content-Length` 头不是合法整数（此时**断开连接**，见下）；或请求体读完后不是合法 JSON 对象（如空、畸形 JSON，或合法 JSON 但不是对象，取 `.get()` 时报错）——**无 body**，此分支**不断开连接** |
| `413` | `Content-Length` 为负数，或超过 4096 字节（`MAX_BODY`，登录体理应就一个口令，超限直接拒）——**无 body**，**断开连接**，见下 |

代码：`auth_stub.py:180-199`（`_login`）。**`login` 在任何分支下都不返回 body**——
全部经由只发状态码的 `_status_only`（`auth_stub.py:122-129`），整个函数从未调用会写
body 的 `_json`。`400`/`413` 两种拒绝会先 `close_connection = True` 再回状态码
（`_reject_body`，`auth_stub.py:170-178`），理由见「安全约定」第 5 条——这不是随手
加的动作，是实测踩过坑之后加的。

### `POST /api/auth/logout`

| | |
|---|---|
| 请求体 | 不读取、不解析——即使带了 body 也不看 |
| `204` | 总是如此，与调用方此刻是否持有有效会话无关——响应带 `Set-Cookie`，把 cookie 覆盖成一个立即过期的值（`Max-Age=0`，值为空串），**无 body** |

代码：`auth_stub.py:164-166`。**注意**：`logout` 不校验当前 cookie 是否有效，未登录
（未带 cookie）调用它同样返回 `204` + 一个过期 cookie。它做的是"让客户端清空自己的
会话状态"，不是"服务端撤销某个已验证的会话"——这与直觉（"要先登录才能登出"）不符，
但代码就是这么写的，按代码为准。这也间接说明了一个边界：因为会话是无状态签名、服务端
不存会话表，`logout` **没有能力**吊销一个已经泄漏出去的 token；已泄漏的 cookie 在有效期
内依然有效，`logout` 拦不住它。唯一的吊销手段是换掉 `AUTH_SECRET`（所有既有签名会同时
失效）。

## 三条不变量

这是本契约的核心——`verify` 站在 nginx `auth_request` 的关键路径上，对**每一个**
`/api/core/*`（或其他被保护前缀）的业务请求先做一次内部子请求，三条不变量都是围绕
"它绝不能成为整个受保护面的瓶颈或单点故障"这一件事展开的。

### 1. `/api/auth/verify` 只返状态码，不返 body

`_status_only`（`auth_stub.py:122-129`）的注释直接写明理由：

```
"""/verify 与 /login /logout 用。**不返回 body** ——
nginx 的 auth_request 忽略 body，返 body 纯属浪费。"""
```

`do_GET` 里 `verify` 的两条分支（`auth_stub.py:157`）都是 `self._status_only(204 if
token_valid(token) else 401)`，从未走过 `_json`。**违反后果**：即便未来实现在
`verify` 里夹带 body（比如想顺便回点什么调试信息），nginx `auth_request` 依然会照样
丢弃它——那段 body 不会到达业务请求的响应里，纯粹是浪费带宽和实现复杂度，还会给人
一种"它返了 body 我就能读到"的错觉，一旦真有人在 nginx 侧假设能读到就会撞上
`auth_request` 天生不透传响应体的限制。

### 2. `verify` 不做 IO、不查库

`token_valid` 的 docstring（`auth_stub.py:90`）："只做签名与过期校验。不查库、不做
IO —— 它在每个业务请求的关键路径上。" 实现本身也确实如此：整个函数只有字符串切分、
一次 HMAC 计算、一次整数比较（`auth_stub.py:95-103`），没有文件、网络或数据库调用。
**违反后果**：nginx `auth_request` 是**同步**子请求——业务请求必须等 `verify` 返回
才会继续被转发。一旦 `verify` 里混入查库或任何网络调用，它的延迟会**叠加到每一个**
被保护的业务请求上；数据库或下游服务的一次抖动，就会拖慢甚至拖挂整个受保护面的响应
时间。这不是"稍微慢一点"的问题，而是把一个本该是纯计算判断的端点，变成了系统新增的
单点故障源。

### 3. `verify` 任何内部错误都必须收敛成 401，不许裸奔成 500

`token_valid` 用一个宽 `except` 把所有异常都收成 `False`（→ 上层映射成 401）：

```python
# auth_stub.py:95-103
try:
    ts_str, sig = token.split(".", 1)
    if not hmac.compare_digest(sig, _sign(ts_str)):  # 定时安全比较，别用 ==
        return False
    issued = int(ts_str)
except Exception:
    return False
current = int(time.time() if now is None else now)
return 0 <= current - issued <= SESSION_TTL
```

配套防御：`_cookie_value`（`auth_stub.py:106-114`）自己手写 Cookie 头解析、不依赖
标准库的 `http.cookies`，注释点明原因——"畸形头在那个模块里会抛"，即拿掉这一层自解析,
一个精心构造的畸形 `Cookie` 头就可能在进入 `token_valid` 之前先把异常抛到
`token_valid` 接不住的地方。两处合起来保证了从"读 Cookie 头"到"判定有效性"的整条
路径上，任何输入（哪怕是刻意构造的畸形输入）最终都落在 `401`，不会裸露成 `500`。

**违反后果**：nginx `auth_request` 对非 `200`/`204`/`401`/`403` 的返回一律当成错误
处理，进而让整个上游请求失败（通常表现为 `500`）。如果哪个分支忘了兜底、裸抛了异常，
auth 服务里一次意料之外的故障（比如签名解析边界情况、时间戳越界）就会**连坐**让
`/api/core/*` 全部业务请求集体报错，即使业务后端本身完全健康。宁可错误地拒绝一个
合法用户（后果是重新登录一次），也不能让 auth 的一次抖动波及全部受保护流量——这正是
把"内部错误"故意映射成"未认证"而不是"服务器错误"的理由。

## 消费方怎么接

`verify` 是设计给 nginx `auth_request` 指令用的内部端点，接法要点：

- 承载 `verify` 的 location 必须标 `internal`——它不是给外部直接访问的路径，只服务
  nginx 内部的子请求（对外暴露它没有意义，`verify` 本来就只回 `204`/`401`，暴露出去
  唯一效果是让别人多一条路径去探测/打这个端点）。
- `proxy_pass_request_body off`（配合清空转发的 `Content-Length`）：`verify` 从不
  读取请求体（不变量 2 的直接推论），原样转发业务请求的 body 给它纯属浪费。
- 通过 `error_page 401 = @xxx` 把 `verify` 的 `401` 转成业务上想要的动作（重定向到
  登录页、或直接把 `401` 透传给客户端，取决于消费方是页面还是 API）。

一份可直接用的配置片段（假设 stub 按默认值监听在 `127.0.0.1:8010`）：

```nginx
upstream auth_gate { server 127.0.0.1:8010; }

server {
    # ... 其他 server 级配置 ...

    # 内部子请求专用：不对外暴露，不转发请求体
    location = /internal/auth-verify {
        internal;
        proxy_pass http://auth_gate/api/auth/verify;
        proxy_pass_request_body off;
        proxy_set_header Content-Length "";
        proxy_set_header Cookie $http_cookie;   # verify 只认这一个头
    }

    # 受保护的业务前缀
    location /api/core/ {
        auth_request /internal/auth-verify;
        error_page 401 = @need_login;
        proxy_pass http://nexus-core:8000;
        # ...
    }

    location @need_login {
        return 302 /login/;
    }

    # auth 自身的端点（health/verify/login/logout）直接反代，不经过 auth_request——
    # 自指死锁：验证接口不能要求先通过验证
    location /api/auth/ {
        proxy_pass http://auth_gate;
    }
}
```

## 换实现要满足什么

任何想替换 `stub/auth_stub.py` 的实现，只要满足下面这份清单，组装层（nginx 路由、
`tools/install.py` 的依赖解析）**零改动**——它们只认路径和状态码，不认背后是一个
标准库脚本还是一整套带数据库的服务：

- [ ] 实现「四个端点」一节列出的全部四条路径、方法、以及每个状态码的含义
      （含 `verify`/`login`/`logout` 三者"不返回 body"这条）
- [ ] 满足「三条不变量」全部三条，尤其是 `verify` 的**无 IO** 与**异常一律收敛成
      401** 这两条——这是最容易在"顺手给 verify 加个日志查询"或"顺手校验一下账号是否
      被禁用"时被破坏的两条
- [ ] 会话 cookie 具备：`HttpOnly`、`SameSite=Lax`、`Secure`（可经配置关闭，仅用于
      本机 HTTP 调试，**默认必须开启**）、`Path=/`（cookie 名不强制叫
      `cockpit_session`，但沿用同一个名字能让现有 nginx/前端配置零改动；换名字则消费方
      需要同步改）
- [ ] 口令或任何凭证的比对使用抗时序攻击的比较方式（见「安全约定」第 2 条）
- [ ] 缺失关键配置（等价于 stub 的 `AUTH_PASSWORD`）时**拒绝启动**，不接受弱默认值
      （见「安全约定」第 1 条）

**不要求**：cookie 值的具体编码方式。stub 用的是`<时间戳>.<HMAC 签名>`的无状态签名
（服务端不存会话表），换实现完全可以换成服务端会话表 + 随机 token，只要仍然满足上面
列出的 cookie 属性与「三条不变量」。

## 安全约定

以下每一条都能在 `auth_stub.py` 里字面对上具体代码，不是本文档臆造的最佳实践清单。

**1. 缺口令必须拒绝启动，不许有弱默认值。**

`_require("AUTH_PASSWORD")`（`auth_stub.py:50-58`，在 `72` 行被调用取值）：环境变量
为空就直接 `sys.exit`：

```
❌ 缺少环境变量 AUTH_PASSWORD —— 拒绝启动。
   这不是 bug：一道没有口令的门等于没有门。
```

模块级 docstring 把这条讲得更直白（`auth_stub.py:29-32`）："给了就一定会有人原样
部署上公网……这条是故意的，别'为了方便'加回默认值。" 默认值的问题不是"这次会被滥用"，
是**必然**会被滥用——只要默认值存在，总会有人图省事直接把服务跑起来而不设置真实口令，
而"跑起来了"本身会给人一种"配好了"的错觉。拒绝启动比"用了不安全的默认值但至少能跑"
更安全：前者的失败是**响亮**的（部署者当场看到报错、当场就得去设置），后者的失败是
**沉默**的（系统一切正常运行，直到被攻破那天才会有人发现）。

**2. 口令与签名的比较必须用定时安全比较，不用 `==`。**

两处都用了 `hmac.compare_digest`：登录口令比对（`auth_stub.py:196`）与 token 签名
校验（`auth_stub.py:97`），各自紧跟一行注释点明理由——"定时安全比较：用 `==` 会让
口令长度和前缀从响应时间里漏出来"。Python 的字符串 `==` 逐字符比较、遇到第一个不同
字符即短路返回，耗时与"猜对了多长的前缀"成正比——攻击者可以靠测量响应时间，一个
字符一个字符地把口令或签名"蒸馏"出来（时序侧信道攻击）。`hmac.compare_digest`
保证比较耗时只与**输入长度**相关、不与内容是否匹配相关，从时间维度切断了这条侧信道。

**3. 日志不记 cookie、不记 body。**

`log_message` 覆写（`auth_stub.py:201-209`）只把方法与状态码这类摘要信息写进日志，
注释直接点明理由（`202-203` 行）："只记方法与状态码，**不记 cookie、不记 body**——
账号服务的日志是最容易把凭证漏出去的地方。" auth 服务的日志一旦被共享（贴进 issue
求助、被同机其他有权限的进程读取、被日志采集器转发到第三方），记录了明文口令或有效
会话 cookie 的日志条目等于把凭证连本带利送出去——日志的访问控制通常比数据库更松，
这类泄漏往往是在"顺手 debug 打印一下 body"时不经意间发生的。

**4. 日志必须截断。**

同一处（`auth_stub.py:208`）：`line = (fmt % args)[:200]...`，截到 200 字符。注释
点明攻击面（`auth_stub.py:205-207`）：`BaseHTTPRequestHandler` 的
`send_error`/`log_error` 会把**攻击者可控的原始字节**（畸形请求行、超长 URL）塞进
日志格式串里。不截断意味着任何匿名请求方都能任意控制服务端日志文件的内容与体积——
可以是拒绝服务（灌日志撑爆磁盘），也可以是日志注入（伪造出看起来像是别的合法日志行
的内容，误导之后看日志排障的人）。

**5. 拒收请求体时必须断开连接。**

`_reject_body`（`auth_stub.py:170-178`）在回 `400`/`413` 之前先把
`self.close_connection = True`。这是**实测发现的真 bug**，注释原文写在代码里：

```
实测（2026-09-16）：早退而不读完 body，剩下的字节会被当成**下一个请求行**
解析，于是 9KB 的 'aaaa...' 变成一条 400 日志把整个载荷打进日志里 ——
既是协议错位，也是攻击者可控的日志写入。断连是唯一干净的出路。
```

原理：HTTP/1.1 默认 keep-alive（`auth_stub.py:119` 设了
`protocol_version = "HTTP/1.1"`），同一条 TCP 连接上的请求按字节流依次排列。服务端
如果在 `Content-Length` 声明的字节数**读完之前**就提前回复、并试图在同一连接上继续
处理"下一个请求"，那些没读完的旧请求体字节会被误当成新请求的起始行去解析——攻击者
故意构造一个超限 body（触发 `413` 的场景）就能让剩余字节被当作畸形请求行喂给
`log_message`（撞上第 4 条截断保护，但依然是协议层面的错位），并且此后这条连接的
状态已经乱掉，后续在这条连接上的请求行为不可预期。断连
（`close_connection = True`）强制客户端另开一条干净连接，是唯一能干净终止这种错位
的办法——比"想办法读完剩余字节再回复"更简单，也更不容易漏掉某个分支。

## 占位实现

`stub/auth_stub.py` 是本契约的参考实现：纯标准库、零第三方依赖。这个目录同时是安装器的兜底位置：`tools/install.py` 在没有任何
模块提供 `auth.gate.v1` 时，会按顺序找 `contracts/auth.gate.v1/stub/`，找到就把占位件
起起来。这正是为什么这份契约与这份 stub 必须放在这个固定路径下，不能改名或挪位置。
怎么把它跑起来写在 `stub/stub.yaml`。

- **纯标准库，零依赖**：只 `import hashlib / hmac / json / os / secrets / sys / time`
  与 `http.server`（`auth_stub.py:37-44`），不需要 `pip install` 任何东西。这是有意
  为之的约束，docstring 原文写得很直接（`auth_stub.py:13-15`）："这个 stub 的全部
  意义是'拉下来就能跑'。它一旦需要 pip install，就失去了当占位件的资格。"——占位件的
  价值就是"零安装摩擦地把契约跑起来、验证组装层能不能接得上"，一旦引入依赖，就要处理
  版本锁定、虚拟环境、依赖安全更新，这些是占位件本不该背负的负担。

- **环境变量**（`auth_stub.py:21-27`，`50-76`）：

  | 变量 | 必填 | 默认值 | 说明 |
  |---|---|---|---|
  | `AUTH_PASSWORD` | ✅ | 无——缺失直接拒绝启动 | 登录口令 |
  | `AUTH_SECRET` | ❌ | 未设则每次启动随机生成（`secrets.token_hex(32)`） | 签 cookie 用；随机生成意味着**每次重启，全部既有会话立即失效**——单机自用可以接受，需要会话在重启间存活的部署必须显式设置 |
  | `AUTH_COOKIE_SECURE` | ❌ | `true` | 本机 HTTP 调试须显式设 `false` |
  | `AUTH_BIND` | ❌ | `127.0.0.1:8010` | 监听地址 |
  | `AUTH_SESSION_DAYS` | ❌ | `30` | 会话有效期天数 |

- **跑法**（`auth_stub.py:17-19`）：

  ```bash
  AUTH_PASSWORD='一个真正的口令' python3 auth_stub.py
  # 本机 HTTP 调试还要加：AUTH_COOKIE_SECURE=false
  ```
