### §2.1 事件信封 yq-event/v1（**最不可回滚的一节**）

系统里发生的每件事都写成一个 JSON，投进**唯一的写入口**。信封所有事件共用，
载荷 `data` 按 `type` 分型。**扩展 = 新增 type，不改信封。**
消费者**必须静默忽略**自己不认识的 type（Postel 法则）。

```jsonc
{
  "spec":       "yq-event/v1",
  "id":         "evt_a1b2c3",              // 本条事件的标识
  "dedupeKey":  "timer:sess_20260729_01",  // 防重键，见 §2.2
  "type":       "session.completed",
  "user":       "u_local",                 // 认证后置期恒为此常量
  "source":     "timer-backend",           // 谁报的：自有后端 / 学生脚本
  "time":       "2026-07-29T10:00:00+08:00",   // 事情发生的时间，见 §2.3
  "recordedAt": "2026-07-29T10:00:03+08:00",   // 系统收到的时间，服务端盖章
  "subject":    { "tier2": "学习", "tier3": "英语",
                  "project": "p_1", "task": "t_45" },   // 见 §2.4
  "data":       { "durationSeconds": 1800 },
  "flags":      ["no_growth"],             // 见 §2.5
  "ai":         { "generated": true, "confidence": 0.87, "confirmed": true }
}
```

**必填**：`spec` `id` `dedupeKey` `type` `user` `source` `time` `recordedAt` `subject`
**选填**：`data`（按 type 定型）、`flags`（默认 `[]`）、`ai`

### §2.2 防重：`dedupeKey`，不是 `id`（人类裁决 2026-07-29）

- **唯一约束 = `(user, source, dedupeKey)`。** 同一防重键重复提交只生效一次。
- `id` 是这条事件的标识，`dedupeKey` 是**业务意义上"同一件事"的键**。两者是不同的东西，
  **不许当作同义词实现**。同一件事被重试提交时，`id` 可以不同，`dedupeKey` 必须相同。
- 由**产生方**负责给出一个稳定的 `dedupeKey`（例：计时器用 session 标识，日记链路用日记标识）。
- 起源：花园现有的"按日记防重复"泛化而来——从 `diaryId` 泛化成 `dedupeKey`。

### §2.3 双时间：`time` 与 `recordedAt`（人类裁决 2026-07-29）

**两个时间字段各管各的，不许合并成一个。**

| 字段 | 含义 | 谁给 | 用途 |
|---|---|---|---|
| `time` | **事情发生的时间**——展示给用户的那个 | 客户端提供，可以是过去 | 花园长在哪一天、统计归到哪一天 |
| `recordedAt` | **系统收到的时间** | **服务端盖章，客户端说了不算** | 重放排序、审计、对账 |

**为什么必须两个**：学生要能补交昨天的记录（`time` 在昨天），
而重放与排序必须不受补交扰动（按 `recordedAt`）。**合成一个就必然牺牲其中一件。**

`recordedAt` **永不可改**；`time` 一经提交也不可改（要改历史 = 追加修正事件）。

### §2.4 `subject`：分类轴是公开契约，内部 ID 是选填（人类裁决 2026-07-29）

```jsonc
"subject": {
  "tier2":   "学习",   // 必填。受控分类词表
  "tier3":   "英语",   // 必填。学生只需写这两个
  "project": "p_1",    // 选填。仅系统内部产生的事件才有
  "task":    "t_45"    // 选填。外部事件留空即合法
}
```

**`tier2` / `tier3` 不是"分区的名字"和"项目的名字"，而是一套受控的分类词表。**

这个区别是全部要害：如果它是可变实体的显示名，改个名就污染全部历史；
而作为分类标签，**分类是它自己的事实，不是别人的副本**，
分区/项目的显示名怎么改都不触碰它。
这也本来就符合花园模型——成长树按 tier2+tier3 生长，每个小分类 10 阶段，
**分类轴是一等的领域概念**。

配套两条硬约束：

1. **可变实体的显示名一律不进事件。** 项目改名 = 追加 `project.renamed` 事件；
   视图在读取时按 ID 现查名字。
2. **`project` / `task` 永远选填。** 外部事件没有它们照样合法——
   这是"自有后端与学生走同一入口"能够成立的前提，不是宽容。

依据（通行经验）：事件字段自第一天起即视为公开 API；内部紧耦合消费方用 ID、
外部松耦合消费方用副本；CloudEvents 的 `subject` 是给中间件做过滤路由的、
不是塞领域对象的地方。本项目**同时有两类消费方**，故分层：分类轴对外，ID 对内。

### §2.5 `flags`：暂行——谁都能贴（人类裁决 2026-07-29）

- `flags` 是贴在事件上的字符串数组，如 `["no_growth"]`。
- **贴什么贴纸 = 数据入库时决定；每张贴纸导致什么行为 = handler 代码焊死。**
  改行为必须改代码、过 review。
- **本阶段任何来源都可以贴**，包括学生脚本。后果：学生可以给自己的事件贴 `no_growth`，系统会认。
- **本条标记为「暂行」，不是永久不变量。** 将来收紧只需加一份"仅系统可贴"的清单，
  **不需要改信封**，因此不违反 C2。

### §2.6 其他固定不变量

- **单一事实来源，星型派生**：所有写操作进唯一写入口，事实落库后派生各视图投影。
  四个前端**没有任何通信路径**，它们只是同一份事实的四面镜子。
- **`events` 集合只增不改不删**；修正历史 = 追加修正事件。
- **所有投影 handler 幂等**，只写自己的投影集合，**禁止发新事件**（防连锁反应）。
- **`projector/registry.py` 的 DISPATCH 表是全系统唯一联动真相**，任何修改单独成 commit。
- **占比 `shareOfPlan` / `shareOfProject` 是 0–100 百分数，不是 0–1 小数。**
  空闲态相关字段为 `null` **不是 `0`**。
- **认证后置的兼容锚点**：一切文档照常带 `user` 字段，写死 `"u_local"`。
  **今天省认证，不省字段。**

### §2.7 nexus-core 必定分拆

模块内的子边界（`events` / `timer` / `planner` / `proposals` / `views` / `projector`）
**＝将来的模块边界**，不按"现在方便"切。
**跨子边界只准调用对方 `service.py` 的公开函数**；只有 `repo.py` 允许碰数据库。
目标是分拆那天是**「搬目录」，不是「重写」**。

## §3 环境与边界

- **跨模块契约落 `contracts/`（仓根一级目录，人类裁决 2026-07-29 · 方案 A）。**
  理由：事件标准要**对外公开发布**，埋在 `agents/reference/` 里名不正；
  它也不属于任何单个模块（nexus-core 产出、ai-gateway 消费、学生外部消费），
  更不能放进 nexus-core——那个模块之后要拆，契约会跟着被拆走。
- 每个模块一个独立 Git 仓 + 一个远端（`dblsc1/cockpit-*`，private）。
  **配了远端不等于闸门通电**：必须故意造一次该被拦的推送、确认它真拦住。
- 密钥只从 env / 专用密钥目录注入；**关键配置缺失立即失败，禁止弱默认值**。
  绑定地址**不得默认 `0.0.0.0`**。
- `nexus-core` **不持有任何 LLM 密钥**——那是 ai-gateway 的事，物理隔离是设计的一部分。
- 运行数据、备份、缓存不进仓。不可再生的上游输入固化在
  `agents/reference/upstream/`（**只读**，改造在模块 `code/` 下做）。
