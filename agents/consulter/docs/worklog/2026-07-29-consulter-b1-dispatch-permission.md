`run_agent.sh` 第 37 行：`args=(-p --agent "$role" --output-format json)` —— **没有任何权限参数**。
派出去的 agent 原话「写权限未授予，一个字都落不了盘……本次留痕为零」，
而 diary 记的是 `{"event":"run_agent","rc":0}`。

**三个模块的 run_all.sh 一个没修，系统认为全做完了。**

## 这是同一个形状的第五次，而且在最要命的位置

我用三轮时间批评「撒谎式成功」：install-gates 静默跳过却报已安装、
修撒谎式成功时自己撒谎、门禁红仍可推送……**每一次我都只修了被指出的那一处。**

铁律 23 是我写的：「修缺陷必须问这个形状还出现在哪」。
我写完它之后，**至少四次只修实例没扫类**。这条铁律对我自己的执行率是零。

而 `run_agent.sh` 是**派活主干**：所有派出去的活都会这样"完成"。
比前面任何一处都严重——前面的坑是某条路径上的，这条是**所有活的必经之路**。

## 修法两半，缺一不可（CFO 的判断，采纳原话）

**① 传权限参数**：`--permission-mode`（默认 `acceptEdits`，
`AIMERGENT_AGENT_PERMISSION_MODE` 可覆盖）。

CFO 提出「范围就是路签划的写区，路签已声明写边界、权限却是另一套，这两个本该是同一个东西」——
**方向对，但 harness 做不到**：它的权限模型没有「只许写这几个目录」这一档。
所以现实分工是：**harness 只管「能不能写」，路签 + `checks/_common/05` 在提交层管「能写哪儿」。**
两者仍是同一件事的两半，只是落在不同层。派活时若该角色没有路签，现在会明确警告。

**② rc=0 不能当完工**：派活前后各取一次工作树快照（`git status --porcelain` + HEAD），
**rc=0 且零改动 → 判 rc=3 未完成**，并直指最可能的原因。
这就是铁律 12「不接受口头已完成」的机械化。
只读任务（纯审阅、只出结论不改文件）用 `AIMERGENT_ALLOW_NO_OUTPUT=1` 放行，记账。

diary 现在多记 `landed` 与 `perm` 两个字段，"派出去到底落没落盘"从此可统计。

## 一处我没验、必须说清

**权限档的具体行为我没有实跑验证**——真跑会起 Claude 进程、花人类的额度，我不替他决定。
默认取了最保守的 `acceptEdits`。若 agent 报的是「不能执行命令」而非「不能写文件」，
说明 Bash 仍被门控，需换 `bypassPermissions`。

**但这次不验也不会静默失败**：landed 检查会立刻把它变成 rc=3 并打印该换哪个档。
**这正是「加断言」的价值——我不确定的地方，让机器替我确定。**
