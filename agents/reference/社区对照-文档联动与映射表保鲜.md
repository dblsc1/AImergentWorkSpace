# 文档联动检查与映射表保鲜 · 社区对照（2026-07-30）

> 结论供 doc-map/检查单理顺用，来源链接在文末。

## 1. 「改代码必改文档」社区怎么拦

- **两档共识**：「文档感知」类（改了 src 没改 docs）用 **warn**（Danger JS 默认形态，
  改 fail 一行变硬拦）；**硬拦只对可判定事实**（表态文件存在 / exit code），
  永远不硬拦「文档写得对不对」。
- **Changesets 是最成熟的硬拦范式**：不检查你改了哪片文档，而是强制 PR 自带一份
  「表态文件」（bot 软提醒 + CI `changeset status` exit 1 硬拦）——
  **与我们 docs_reviewed 表态完全同构**，我们独立收敛到了社区最佳实践，
  且带 reason 字段比它多一层可审计。
- Chromium PRESUBMIT 三档（fail/warning/notify）＝我们的 硬拦/提示/忽略；
  CODEOWNERS 只保证「有人看」不保证「同批改」。

**对照结论**：我们的 11 号（表态硬拦）+ 反引号反查（仅提示）分层与社区共识一致，
不用改结构。

## 2. 映射表（doc-map.tsv 类）怎么保鲜

**靠工具校验，不靠约定**——CODEOWNERS 生态已有成熟 lint（mszostok/codeowners-validator、
codeowners-validation）：查语法、属主真实存在、**pattern 必须匹配到 ≥1 个文件**、
无主文件报警、shadowing。Rust tidy 把「自动化配置引用的路径必须真实存在」做成 CI 硬红。

**可直接抄的形状（对 doc-map.tsv）**：
1. 每行 code 路径 glob 必须匹配 ≥1 个已跟踪文件（死条目=改名/删除后残留，100% 可机械检测）
2. 每行 doc 路径必须存在（12④ 已部分覆盖）
3. **无主检查兜底**：不被任何条目覆盖的新顶层目录 → 报警「新区域没登记治理关系」
   ——这补上了「机器测不出新代码区域没登记」的唯一盲区

**另一条路线是消灭表**：docs colocation（J3 已做）——同目录后就近判定不需要表；
社区提醒「proximity isn't accuracy」，仍需检查兜底（我们的 checks/14 就是）。

## 3. policy-as-code 附问

Conftest（OPA/Rego）支持仓库治理场景（校验 JSON/TOML/Dockerfile/PR 元数据），
「每条政策必有可执行检查」是其口号——但都是**逐条手写** policy + CI 强制，
没有从散文自动生成检查的方案。我们铁律 23 的「修复必留断言」同形，无现成件可买。
