## 一、这套东西在解决什么

多个 AI 并行改同一批代码，会稳定产生四种事故。整套设计是围着这四种建的：

| 事故 | 表现 | 对策 |
|---|---|---|
| **未受控双写** | 两个 agent 同时改同一片代码，互相覆盖 | 写区路签（发签自愿、验签强制） |
| **口头完成** | agent 说干完了，实际一个字没落盘 | 报告必须 git 化 + 落盘核实 |
| **撒谎式成功** | 脚本报成功，实际什么都没做 | 关键路径缺件即 die；退出码 0 不等于干完 |
| **文档滞后** | 代码改了、文档没跟，下一个人照旧文档实现 | 治理关系表 + 五时点核对 |

**贯穿全局的一条**：**成功的外观必须携带「它成功了什么」的证据。**
门禁绿不等于验过、`rc=0` 不等于落了盘、面板有数据不等于是你要的那个仓。

## 二、角色与分工

### 项目级（三个，**并列**，不是上下级）

| 角色 | 干什么 | 不干什么 | 落点 |
|---|---|---|---|
| **CFO** | 收人类指令 → 拆成模块任务 → 决定叫哪个 arbiter；建模块、建角色；维护 `doc-map.tsv`；合并到 `dev` | 不写业务代码、不看单个 diff 的技术对错、不碰 `main` | `agents/cfo/` |
| **consulter** | 架构问题、观察 CFO 输出找**系统性偏差**、**维护框架本身（掌管框架仓 git）** | 不做逐单审核（归 reviewer）、不裁决架构方向 | `agents/consulter/` |
| **人类** | 架构方向、远端与部署授权、`doc-map` 增删、`dev → main` | — | — |

**为什么 consulter 不在 `agents/cfo/` 下面**：它监督 CFO 的产出（谁审谁的唯一事实源：
`agents/protocol/supervision.md`）。挂在 CFO 名下＝结构上说它归 CFO 管，
与「谁写的谁不审」直接打架。**位置即归属**，这条在本框架里被反复用到（`doc-map.tsv` 放 `agents/cfo/` 同理）。

### 模块级（四个）

| 角色 | 谁建 | 干什么 | 边界 |
|---|---|---|---|
| **arbiter** | CFO | **定本模块总体结构**（先于一切派活）、拆单派活、维护契约、裁决打回；架构级问题**有权也有义务**上报 | 禁写 `code/`、`review/` |
| **programmer** | arbiter | 实现、自测、留痕，仅此三件 | 契约只读；禁写 `review/` |
| **programmer_reviewer** | arbiter | 审**代码** | `code/` 只读，禁改业务代码 |
| **module_reviewer** | CFO | 审 **arbiter 的规范面**（文档规范/越权/报告合规），交 CFO 前必过 | 不评技术方案 |

写边界在角色卡里**留空**，由 `scripts/new_agent.sh` 生成实例时按分区填实。

### 交叉审核（谁写的谁不审）

```
CFO / arbiter / programmer 的活   →  reviewer 审
consulter 改的框架               →  CFO 审（那不是它的活）
两边都参与的                     →  停下交人类
```

## 三、一次任务的完整流程

```
CFO   aim new-module <名字>            建模块：骨架+门禁+三角色+初始 commit+feat/init
      aim dispatch arbiter <任务单>     出提示词 → 人开 arbiter session

arbiter
  ├─ 出生第一条输出＝考卷（写在 system prompt 里，跳不过）→ aim exam 判卷
  ├─ ① 定模块总体结构，写进 rules.md，**派第一个活之前定稿**
  ├─ ② aim start programmer <任务单> <写区> --docs update:<路径>
  │      起飞单 7 项全过 → 发写区路签 → 出派单提示词
  ├─ ③ aim run programmer <任务单>      起独立进程（子代理开不了子代理）
  │      programmer: 实现 → 自检门 → aim done → **本地 commit（不推）**
  ├─ ④ aim review programmer_reviewer <本地commit>   审的是固定 commit 区间
  │      reviewer: 写 reviewcode 脚本 → aim review-done … approved|rejected
  ├─ ⑤ rejected → aim run programmer --resume（**续用，绝不重开**）
  ├─ ⑥ approved → aim push origin <分支>（先跑门禁 + 校验有 approved 审核）
  ├─ ⑦ module_reviewer 审规范面（交 CFO 前必过）
  └─ ⑧ aim merge <仓> → dev

人类  dev → main（agent 不碰 main）
```

**两处顺序是有意的**：

- **先审后推**：本地 commit 已是不可变、有 SHA 的真实对象，绑它足够。
  好处是**被打回的活永远不上远端**、返修不用 force-push。
  代价：review 时没有 CI 结果 —— 本地 gates/tests 先顶，CI 是推之后的第二道网。
- **续用不重开**：重开＝冷启动重读 handoff + 契约全文。实测一次重开可占整轮子代理消耗三成。

## 四、三层闸门

| 层 | 谁拦 | 拦什么 | 绕过方式 |
|---|---|---|---|
| **派单层** | `exam.sh` | 没读规范的 agent 不放行接任务 | 无令牌；不过就退回重派 |
| **提交层** | `pre-commit` → `mission_complete.sh` | 留痕不全 / 越写区 / 文档没跟上 / 无审核意见 | `AIMERGENT_MISSION_OVERRIDE="<理由>"`（放行但**强制记账**） |
| **合并层** | `arbiter-push.sh` + `merge-to-integration.sh` | 无 approved 审核、门禁不绿 | `AIMERGENT_PUSH_SKIP_GATES`（同上） |

**逃生口是必需品，不是妥协**：没有逃生口的硬闸门，第一次误判就会让人把整个 hook 删掉。
但每次使用都会进控制台的「逃生口使用」那格 —— **规矩可以被绕过，但绕过必须留痕。**

**审核门在 merge，不在 commit**：提交层只要求 `reviewer_opinion` 字段**存在**（`verdict` 可为 `pending`），
合并层才要求 `approved`。否则实现者永远无法先提交形成 candidate，审核就无从开始。

## 五、着陆检查项（三层级联）

```
scripts/checks/_common/     所有角色都跑
scripts/checks/<角色>/       该角色专属
codeagent/<角色>/checks/     本模块给该角色追加的
```

**依次全跑，下层只能加严** —— 与「模块只能加严项目规范」是同一条原则。
增删改查一条检查＝加/删/改对应层里的一个文件，`mission_complete.sh` 永远不用动。

| 层 | 检查 |
|---|---|
| `_common` | 05 写区路签 · 10 worklog · 11 文档同步 · 12 长期文档体检 · 13 门禁新鲜度 · 20 报告已提交 · 40 分支纪律 · 60 路径可解析 · 70 审核意见 · 90 依赖漂移 |
| `arbiter` | 30 子报告落点 · 50 契约同步 · 80 任务单四小节 |
| `programmer` | 81 写边界 |
| 两个 reviewer | 82 审核区间（`review_target` 必须 exact） |

角色解析：`AIMERGENT_ROLE` → 从暂存的 worklog 路径推断 → 只跑 `_common`。

## 六、文档纪律（这套东西最容易塌的一环）

### 关系从哪来（三个来源，主干是人维护的）

1. **`agents/cfo/doc-map.tsv`** —— 长期文档治理哪片代码区域（项目级，**CFO 维护**）
2. **模块级约定**（不用登记）—— `code/<模块>/code/**` → 该模块 `contract.md` + `AGENTS.md` + `文档地图.md`
3. **反引号反查** —— 只作提示，不硬拦（抓到的多是偶然提及，粒度太细）

**主干为什么不能是自动反查**：`contract.md` 治理 `code/backend/**`，
**哪怕它正文里一个路径都没写**。关系是语义的，机器推不出来。

### 五个时点各算一次（同一个算法：`scripts/lib/docmap.sh`）

| 时点 | 谁做 |
|---|---|
| 派活 | `dispatch.sh` 把判据嵌进提示词 |
| 起飞 | `mission_start.sh` 按写区**预告**可能牵动的文档 |
| **干活中随时** | **`aim docs`** —— 「我改了 1 2 3 → 必须看 a b c d」 |
| 着陆 | `checks/_common/11` 逐条核 |
| 推送/合并 | 按**整段区间**复核（着陆只看单次暂存，分支整体会漏） |

**抽成一个库的理由**：同一个问题被问五次，每处各写一份，五份迟早互相漂移，
漂移之后哪份是对的没人说得清。**同一个问题只允许有一个答案的来源。**

### 每份文档只有两种处置

- **改到位** → 和代码同批提交
- **不用改** → `report.json` 写 `{"action":"no-change-needed","reason":"…"}`

**写「不用改」完全可以，写不出理由才是问题。** 机器只查有没有表态；
**理由的成色只能人审** —— 模块内归 arbiter，波及框架层归 CFO。

## 七、留痕：四件套，各一个写属主

| 文档 | 时间维度 | 写属主 | 落点（J3/J4 裁决后） |
|---|---|---|---|
| **任务单** | 任务开始 | arbiter 写进实例目录 | `codeagent/<容器>/<编号>/docs/` |
| **worklog**（简短） | 回顾过去（做了什么、**为什么**） | 各角色写自己的 | arbiter `module_docs/worklog/`；programmer `code/<子文件夹>/worklog/` |
| **report.json** | 当下交接（终态 + 升级面；programmer 的＝工作任务书） | 各角色写自己那份 | arbiter `module_docs/`；programmer `code/<子文件夹>/`；详见 `agents/protocol/report-schema.md` |
| **comm.jsonl** | agent 间沟通（发任务/报完成），**每 agent 一份** | 各 agent 自己 | 实例 `docs/comm.jsonl`；arbiter `docs/arbiter.jsonl`；全仓 `logs/diary.jsonl` 只留脚本事件 |
| **handoff.md**（一页纸，**每改必核**） | 面向未来接手者 | 模块级 arbiter；代码侧 programmer | `module_docs/handoff.md`；`code/<子文件夹>/handoff.md`（checks/14 拦） |

**报告链路**：programmer → arbiter → CFO → 人类，每层**只卷摘要 + 路径，不整包塞**。
CFO 与人类只看三格路由：`contract.touched` / `cross_module_impact` / `escalation`，**不读散文**。

**未跟踪 / 工作区脏 / 写在仓外 = 一律按「未产出」处理。**

## 九、已付过学费的坑（判例库摘要，全文见 `agents/consulter/记忆.md`）

**1. 恒定答案** —— 一条永远给同一个答案的检查，等于没有这道门。已实证五种形态：
空区间假绿 · landed 恒真（快照含脚本自己的写入）· 模块门禁恒红（引用的脚本没被装）·
判据仓型不匹配 · 表读不到时检查静默失效。
**审的时候追问：它在什么情况下永远通过？永远失败？两个答案都必须是「没有这种情况」。**

**2. 撒谎式成功** —— 本轮出现五次，最严重一次在派活主干上（agent 无写权限、一字未落盘却退 0）。
**通则：关键路径缺文件必须 die；可选件缺失必须打印「已跳过」；唯一不许的是静默跳过后报成功。**

**3. 只修实例不修类** —— 铁律 23 的由来。同一个 bug 换个载体就活下来。
见到缺陷先问「这个形状还出现在哪」。

**4. 字面量陷阱** —— 凡是「报告某字面量缺陷」的文档，都会成为那个缺陷的新实例。
讨论 token/占位符的文档必须拆开写，与检查脚本本身是同一条规矩。

**5. 模块级 vs 根仓** —— 撞了四次。模块角色必须在模块仓内派；根仓只有 CFO 与 consulter。

**6. 白名单 `.gitignore`** —— 新增根级文件必须同时加 `!/<名字>`，否则**静默吞掉**。

**7. 错误信息要说该怎么办** —— 只说哪里错会把人引向错误的修法
（去改 `.gitignore`、去找文件、去改 `replace_token`，三条都是死路）。

**8. 反向验证是唯一可信的证明** —— 放入违规 → 必须变红；拿走 → 必须复绿。**看代码不算。**

**入口只有一个**：`scripts/aim`（无参数打印整条生命周期）。
脚本数量不是问题，**「我现在该跑哪个」没有答案**才是问题。

必会的六个：
```
aim                      看流程
aim docs                 我改了这些 → 要连带看哪些文档
aim start --checklist    起飞单 7 项
aim done --list          着陆判据
scripts/selftest.sh      34 条闸门有效性断言（改了门禁必跑）
scripts/gates/check-references.sh   全仓引用完整性（改名/搬家后必跑）
```

**控制台**：`http://100.107.33.121:8787`（tailnet，无鉴权所以不绑 0.0.0.0）。
每个脚本 source 了 `lib/emit.sh`，激活与退出自动上报，面板 SSE 实时显示。
**盯「逃生口使用」那格** —— 它是唯一一个「规矩被绕过」的可见入口。
