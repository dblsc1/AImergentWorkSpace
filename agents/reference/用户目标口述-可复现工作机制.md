## 总目标

构建一套**可复现**的工作机制，让长时间工作的 AI 能**可持续产出高质量代码**，
减少人的机械化测试工作；同时限制 vibecoding 的三大问题：
**不好维护、偏移原目标、原地打转**。

## 1 分工限制爆炸半径，节约 token

- **1.1 多角色分工**：每模块通用 arbiter–programmer–reviewer 架构。
  - CFO 开 subagent 为 arbiter；arbiter 通过 **shell 调用** programmer
    （arbiter 作为子代理时无法再开子代理——harness 嵌套限制，shell 起独立进程绕开）。
  - programmer 读通用提示词；做完由 reviewer 审查；arbiter 读报告收口。
  - ⟦consulter 补充：现框架已有对应件——`aim run` 即 shell 起独立进程；
    项目级另有 CFO / consulter / 人类三方并列，见 `agents/protocol/supervision.md`⟧
- **1.2 硬闸门限制可写范围**（保证事故可控）；可读范围目前较宽松，暂不收紧。
  ⟦现况：写区路签 mission_start → 05-write-lease 验签已落地；读范围无闸门⟧
- **1.3 续用不重开**：目前还是软限制（提示词层面），未做硬约束。

## 2 减少人类介入

- **2.1 自动化测试**
  - 新增功能 **reviewer 要写自动化测试代码**；新增代码也要新增测试。
  - arbiter push 之前走**全量测试**（具体范围待定）。
- **2.2 多级检查单体系**（每个交接点一张单，模块单叠加在通用单上）：
  - arbiter 发任务 → 任务检查单
  - programmer 接任务 → 起飞前检查单；做完 commit → 落地检查单
  - arbiter 收任务 → mission_complete 检查单
  - reviewer 接任务 → review 前检查单；审完 → reviewer 检查单
  - arbiter push 前 → push 前检查单 → 才 push
  - CFO 同样有自己的检查单
- **2.3 明确规定什么时候必须叫人**。
- **2.4 闸门本身的有效性也需要定期检测**（用户标注：还没做）。
  ⟦现况：selftest 已存在且每条新断言要求红/绿反向验证（判例库 2026-07-29 条），
  但「定期」触发机制（CI 周期跑）未闭环⟧

## 3 提示词管理（三层叠加注入）

- 项目通用提示词——每个 AI 自动注入
- 角色提示词——每个角色注入
- 模块提示词——叠加注入到该模块的 AI

## 4 留痕管理（模块内四文档，programmer 检查单逐项含）

1. **worklog** 开发日志：各角色，放代码目录旁，**简短**（用户明确：和之前安排不同）。
2. **jsonl**：AI 之间格式化传递信息——发任务、报完成的记录，只增不减，**每个 agent 一份**。
   注重**沟通留痕**。
3. **一页纸说明**：每次更改都要确认这页说明仍然成立，方便接手；每个模块文件夹内一份。
4. **report.json**：每次交接的详细信息（发任务 + 完成改了什么），技术留痕，放代码文件夹内
   方便查问题；也是 programmer 提示词的重要组成部分——相当于**工作任务书**（每次）。
