# 项目级依赖索引

> **写属主**：CFO arbiter（角色卡职责 5）。模块 arbiter 维护自己的 `provides` / `consumes`；
> 本文件是**跨模块的汇总视图**，用途只有一个：**契约要改时，一眼找到全部消费方。**
>
> 漏登记的模块在变更评审里是隐形的——改契约的人不会知道它存在，
> 而它会在合并之后才炸。新增模块必须同步本表（铁律 11）。

## 已知的登记缺口

nexus-core 尚未建模块，所以上表两条依赖的**供给侧还没有契约文件可以指向**。
这不是可以忽略的形式问题：在 nexus-core 的 `module_docs/contract.md` 落地之前，
两个前端模块的 `consumes` 只能引用 HANDOFF §7.1 的规范性描述。
**HANDOFF 是项目总目标、指导性可改，不是契约**——它随项目进度会变，而契约不该悄悄跟着变。

处置：nexus-core 建模块时，第一件事是把 HANDOFF §7.1 的 views 响应模型
固化成真正的 `contract.md`，然后回来把上表的「依赖的契约」列指向那份文件。
在那之前，两个前端模块的 report 里 `contract.consumes` 必须如实写成待定，
不许指向一份还不存在的契约文件充数。
