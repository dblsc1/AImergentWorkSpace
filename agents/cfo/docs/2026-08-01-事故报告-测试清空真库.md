# 事故报告 · 测试套件清空了生产库

> 责任方：CFO（我）。发现方式：用户问「怎么用 ring 记第一条」，我去查库时发现
> `events` 集合为 0，而我几小时前刚成功跑过一次计时并拿到事件 id。
> **不是用户报的故障，是我自查时撞见的——但也不是我主动核查出来的，是碰巧。**

## 一句话

**测试套件会静默清空你指向的任何数据库，我把真库名传进去跑了测试，
62 个测试挨个清了 62 遍，用户的历史计时记录全没了。**

## 时间线

| 时间 | 事情 |
|---|---|
| 12:23 | 我跑通计时链路，`timer/stop` 返回事件 `evt_782616a53f20`，证明事实已落库 |
| 之后多次 | 我为核实各轮交付，反复跑 `NEXUS_DB_NAME=nexus_core ... pytest -q` |
| 13:10 | 用户问怎么记第一条记录，我查库：`events: 0`、`proj_current: 0` |
| 13:15 | 现场复现：start→stop→`events=1, proj_current=1`，**机制本身没坏** |
| 13:16 | 读 `conftest.py`，定位根因 |

## 根因

`code/nexus-core/code/backend/conftest.py`：

```python
os.environ.setdefault("NEXUS_DB_NAME", "nexus_core_test")   # 第 22 行

@pytest.fixture(autouse=True)
def clean_db():
    """每个测试从空库开始——测试之间不许互相喂状态。"""
    db = get_db()
    for name in _COLLECTIONS:
        db[name].delete_many({})        # 第 39 行
```

`_COLLECTIONS` 覆盖 `events / timer_state / proj_current / zones / projects /
tasks / name_registry / counters` —— **全部八个集合**。

**关键在 `setdefault`**：它只在「环境里没有这个变量」时才用测试库名。
我跑测试时显式传了 `NEXUS_DB_NAME=nexus_core`（真库），
`setdefault` 于是**什么也不做**，测试就照着真库清。

`clean_db` 是 `autouse=True`，每个测试函数前都跑一次。62 个测试 = 清 62 次。

## 为什么这个设计是错的（不是"我不该传错参数"）

作者显然想到了这件事——否则不会特意默认到 `nexus_core_test`。
但他用的是**弱防护**：默认值。默认值只在"你什么都没说"时生效，
而**真正危险的场景恰恰是"你说了、但说错了"**。

正确的形状是**硬拒绝**：库名不像测试库就报错退出，而不是照做。
这与框架自己反复强调的一条完全同构——「关键路径缺文件必须 die；
唯一不许的是静默跳过后报成功」。这里是「静默清库后报测试通过」。

**同一形状今天已经出现过三次**：
- `mission_complete.sh` 推断出角色却不 export → 写区检查静默放行
- `check_bind` 只匹配 `0.0.0.0` 字面量 → 具体 IP 直接绕过
- 本次：`setdefault` 只防"没传"，不防"传错"

共同点：**防护只覆盖了粗心的那一半，没覆盖搞错的那一半。**

## 影响

- **丢失**：`events`（用户的计时历史事实）、`proj_current`（圆环投影）。
  截至事故发现时 `events: 0`。
- **未丢失**：`zones/projects/tasks` 种子数据当时还在——因为我在清库之后
  又跑过 `seed_planner.py` 重建。**这是巧合，不是防护。**
- **实际损失有限**：用户尚未开始真正使用，丢的是我自己测试产生的记录。
  **但如果晚发现两天，丢的就是真实工作记录，且不可恢复**——
  事实是 append-only 设计，没有软删除、没有回收站、没有备份。

## 已做的处置

在 `conftest.py` 加硬拒绝：库名不以 `_test` 结尾就 **die**，不再"你传什么我清什么"。
红绿实测见下方。

## 未做 / 遗留

- **没有备份机制**。事实是 append-only 但没有任何 dump/还原流程。
  真实使用前应该有——丢了就是丢了。**这条我没自作主张做，登记在此。**
- 其余五个模块没有同类风险（无 DB）。但**将来任何新模块接库都会重踩**，
  除非这条硬拒绝进模板。

## 我的过失

1. **传真库名跑测试**。当时的动机是"验证代码在真实数据上也能跑"，
   但那正是最不该用测试套件干的事——它的第一件事就是清库。
2. **跑了至少两次没发现**。中间我还查过库、看到数据在（种子重建后的），
   **误以为一切正常**。
3. 这条本该在我第一次跑测试时就读 `conftest.py` 确认落点——
   我在别的场合反复要求"验落点"，自己在这里没做。
