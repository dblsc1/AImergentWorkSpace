## 起因：实现撞出了一个契约空白

programmer 交付切片 1 后，我复验金链路时 `timer/start` 崩在
`service.py` 第 59 行 `task["tier2"]` —— 它假设分类挂在任务上。

查下来**契约压根没说 `tier2`/`tier3` 存在哪一级**。事件必填它，
但没有任何一处说从哪查。实现者只能猜，猜错了。

**所以这不能算实现的错，是契约留的空白。**

## 顺着这个空白，用户看出了更根本的问题

我原本准备补一条「任务→项目→分类」的查询链路了事。用户的问题是：
**`tier2`/`tier3` 为什么要和 `name` 并列存在？**

一问就露底了：按旧模型的映射，`tier2` 指分区、`tier3` 指项目 ——
**而 `subject` 里已经有 `project` 这个 id 了**。同一个关系存了两遍，
一份字符串一份 id。两份拷贝必然漂：改了名字那份、忘了另一份，历史就自相矛盾。

用户还纠正了我一处框架错误：我在问「分区名和 tier2 是不是同一个东西」，
而**这个问法本身就混了三样** —— id、显示名、分类词。用户一句
「id 和 displayname 本来就不该是同一个东西」把它拆开了。

## 查了通行做法，结论是「两个都要」不是二选一

- **Google API 设计指南**：用层级名做实现标识，要么禁止改名换归属、
  要么准备好处理断链；**正解是两种都提供**。
- **Jira**：数字 issue id 跨项目搬移也不变；人读的 issue key 会随搬移而变。
  文档明写：需要稳定引用的场合一律用数字 id。

所以我先前问用户的「出生地还是现住址」是个**伪问题** ——
那是两个字段各管一件事，不需要一个字段身兼两职。

## 中英文 id：查证结果支持数字方案，反对音译

- **音译会塌陷**：`塔`(tā) 与 `她`(tā) 音译后同一个串，两个名字撞成一个标识。
- **音译方案不止一种**：换个库/换个规则，已生成的标识全变。
- 检索结果明写：**输入全是 CJK 时剥离后得到空串，所以要回退到数字 ID**。

用户原本提的就是数字方案。而**唯一约束压在 opaque `id` 上**这一条，
正好把音译方案最危险的部分卸掉了 —— `key` 算错了不致命，`id` 撞了才是事故。
