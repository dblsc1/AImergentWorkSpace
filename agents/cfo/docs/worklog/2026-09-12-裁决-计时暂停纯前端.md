# 2026-09-12 · CFO 裁决 · 计时「暂停」走纯前端，后端零改动

## 人类原话

- 「加入三个按钮……下半两个一个是完成一个是暂停。最底部是取消不记录，同样的，给计时面板也加上。」
- 「新增一个本次任务暂停按钮（纯前端活）。显示在中心计时圆环和计时面板中。后端接口保持不变。」
- 「暂停应该是不需要动后端的吧，前端停止计时就可以了。不对，上传后端时似乎需要对上开始和结束时间。你准备怎么办？」

## 裁决

后端一段计时 = `timer/start` 那一刻到 `timer/stop` 那一刻。只停前端走秒而后端不停，
暂停的那段照样被记成干活，事后也没有接口能扣掉（events 只追加）。所以：

- **暂停 = 真的调既有 `timer/stop`**：开始到暂停这一段按真实起止入账
- **继续 = 既有 `timer/start {taskId}`**：对同一个任务新开一段
- 两段中间的空白不属于任何一段 → 不记账；任务总时长 = 各段之和，照样准
- "暂停的是哪个任务"只存在本机 localStorage，键 `nexus.timer.paused.v1`，蜂巢与计时台同源共用

规范落在 `contracts/timer-ring-visual-v1.md`「计时控制按钮 + 暂停（纯前端）」。
代价（诚实登记）：一次"工作"在流水里会是多段；中心格走秒在「继续」后从 0 重新数，不是累计。
要显示"本次累计"得另记一份本机累计秒数，这轮不做，人类要再加。

## 追加（同日第二轮）

人类：「暂停后继续需要继续之前时间」「暂停时一样可以取消不记录，按钮不用隐藏」「计时台停止并记录
不需要二次确认」「契约要推」。

- **暂停态的取消怎么算**：问了人类（三选一），裁决 **暂停即入账，取消只作废当前段**。
  否掉的备选：暂停先 cancel、完成时再补登 —— 补登事件的 source 是 `manual-backfill`
  （"回忆填的"证据强度），会把表测的时间标成回忆；且暂停期间的时间只活在一台浏览器里。
  所以暂停态的「取消」不发请求，只放下"继续"，界面说明"暂停前的时间已入账、撤不回"。
- **继续接着之前的时间**：新增累计记忆 `nexus.timer.carry.v1`，只影响显示，入账仍按段。
- 规范 `contracts/timer-ring-visual-v1.md` 同步；两模块同键实现（table / ring 同日提交）。
