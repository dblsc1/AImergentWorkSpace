# 裁决 D18 · 四个前端保持零构建，换库不上构建链

- 角色：cfo · 日期：2026-08-12 · tier：simple
- 触发：甘特 UI 换库讨论。用户问「上 npm 对开源有影响吗」，答完后拍板「保持零构建，只换库」

## 目标

把「前端零构建」从一个**未成文的历史惯例**升级为**成文裁决**，
免得下一轮又有人提议上 vite，再讨论一遍同样的账。

## 用户的痛点（换库的真实动机，不是洁癖）

甘特现用 vis-timeline + vendored timeline-arrows。用户原话整理：
交互难用（缩放/拖拽/标签重叠）、拖动反馈差、不好扩张缩小、不好看、
**「事实只有计划一半高，叠加不好看」**。

前四条是库的交互能力，第五条是我们自己的渲染逻辑。**换库能解决大部分。**

## 我给用户的分析（npm 对开源的影响）

**许可证层面基本没影响** —— npm 包多是 MIT/Apache，且**「依赖」不是「合并」**：
`import` 一个 MIT 库不会让你变成它的证。真正传染的是 GPL/AGPL，
**而那与用不用 npm 无关**（vendored 一份 GPL 代码照样传染）。
**该查的是每个包的 license，不是「用不用 npm」。**

**真实代价在工程面**：上构建链要同时改 nginx 挂载点、nginx-docker 契约、
零密钥确定性 CI、`.gitignore`、行数门禁（打包产物会撞）；
开源可读性从「clone 就能看到跑的东西」退化成「先 `npm i && build`」。
**最要命的是供应链**——一个库拖进几十个间接依赖，vendored 意味着全要进仓、全是信任面。

## 裁决

**换库允许，上构建链不允许。** 第三方库走 vendored 独立 bundle
（UMD/IIFE/standalone ESM 下载进仓，如现有的 `vendor/timeline-arrows.js`），
**只接受 MIT / Apache-2.0 / BSD**（项目将开源）。

确需构建链，走人类裁决另开一条——**不是永久禁止，是不默认付这笔账**。

## 配套动作

已派调研 agent 查候选库的**实际情况**（不凭训练记忆）：许可证要去看 LICENSE 文件
而不是 README badge、有没有独立 bundle（**硬门槛**）、依赖箭头/拖拽/缩放/
计划-事实叠加是否原生支持、能否被 CSS 变量驱动（我们有 design-tokens 契约）。
**查不到的标「未查证」不许猜**——许可证猜错了到开源那天是硬阻塞。
